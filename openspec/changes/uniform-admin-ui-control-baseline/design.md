## Context

管理台前端的控件规格在全站发散。实测数据：`.vue` 文件中 415 个 `<button>`，引用统一按钮类的仅 51 处（约 12%）；手写 `px-* py-*` 内边距组合 33 种；圆角变体 7 种并存。同一行出现 4 种控件高度、3 种圆角是常态。

根因已定位到基础设施：`assets/styles/components.css:112` 的 `.btn` 只定义了 `font-weight`、`border-radius: 12px`、`border`、`cursor`、`transition`、`position`、`overflow`、`letter-spacing`，**不含 padding、height、font-size**。调用点若只写 `.btn` 会得到一个没有内边距的按钮，因此每处都必须自补尺寸，发散是必然结果。同时 `main.js` 同时引入 `main.css`（内部 `@import './components.css'`）与 `global.css`，而 `global.css` 内部 `.btn` 重复定义两次（247、423 行）、`.form-input` 重复两次（324、499 行），叠加 `components.css` 后 `.btn` 共三处定义，级联结果不可预测 —— 这也解释了为何以往改类名常常不生效。

除规格问题外还有三类并存问题：真实数据下恒定的表格列与恒空的数据块仍占版面；用户体系未启用时相关页面仍可手敲 URL 到达并显示整屏空数据；部分页面与组件缺暗色变体，暗色下白卡压深底。

约束：这是运行中服务的管理台，纯前端变更；改动面覆盖几乎全部视图，必须可分步验证与回滚；不希望在一次发布中同时改变样式基础与全部页面。

## Goals / Non-Goals

**Goals:**

- 让样式定义来源唯一，使基础控件类自带完整尺寸规格，从机制上消除「每处自补内边距」的必要性。
- 同类控件在全站（含对外展示页）使用同一档高度与圆角，同行控件对齐同一基线。
- 表格呈现规则统一：内边距一致、数值列右对齐可排序、恒定值列降级、分页单一实现。
- 移除恒无数据的区块与可推导的重复指标，回收版面。
- 未启用能力的页面不可达，依赖未启用特性的界面元素不渲染。
- 暗色模式全覆盖，主题入口收敛为一个但保留两项能力。
- 收敛同构页面与重复布局，移除死代码。

**Non-Goals:**

- 不改动任何后端接口、数据结构与业务逻辑。
- 不改变各页面的功能范围与信息可得性 —— 精简只降低呈现冗余，不删除用户可获取的信息。
- 不修 webhook 配置渲染与通知投递缺陷，那些属另一变更（`fix-webhook-config-render-and-notification-gaps`）。
- 不引入 UI 组件库或设计系统依赖，仍基于现有 Tailwind 与自有类。
- 不重做 8 种推送平台的弹窗表单结构。
- 不为服务倍率补基准校验。

## Decisions

**决策一：先修样式来源，再补基础类，最后逐页替换**

实施顺序固定为四步：① 移除 `global.css` 重复段使来源唯一；② 给 `.btn` 补 sm/md/lg 尺寸变体并确立卡片与表格基线；③ 逐页把手写 `px-* py-*` 替换为基础类；④ 删死代码与收敛重复实现。

顺序不可颠倒。若先逐页替换类名，页面仍会受三份重复定义的级联影响，替换结果不可预测，且验证时无法区分「类名没改对」与「样式被覆盖」。考虑过的替代方案是「一次性全量重写样式与页面」，否决原因是无法分步验证，一旦出现回归难以定位到具体环节。

**实施期修正：去重的权威来源与规模都与预期不同。** 动手前的假设是「删 `global.css` 的重复、以 `components.css` 为源」。实测发现相反：`main.js` 中 `global.css` 后于 `components.css` 加载，因此 `components.css` 中 **39 个**同名选择器的定义**完全失效**，而 `global.css` 版本才是实际生效的；且 `global.css` 版本使用主题变量（如 `var(--border-color)`），`components.css` 版本是硬编码 `rgba(255,255,255,...)`——若以后者为源会**破坏暗色模式**。因此改为保留 `global.css` 版本作为权威来源，删除 `components.css` 中 39 个失效定义，并删除 `global.css` 内部重复的整块副本（12 个选择器，去注释后逐条等价）。重复规模也远超预期的「4 个类」。第一、二步完成后以注入探针比对 20 个类 × 15 个计算属性，改动前后完全一致，验证「视觉不变」这一安全阀。

（实现注记：按选择器字符串删除规则时，须把前导注释一并纳入规则起止范围，否则带注释与不带注释的同名规则会被区别对待，导致删除结果不一致。）

**决策二：尺寸取值另行按基线定义，不复用对外页 scoped `.btn`**

原计划复用 `LandingView` / `StartView` 中的 scoped `.btn`，认为其「内边距规格完整、直接提升为全局即可」。实测其取值为 `padding:12px 22px; border-radius:980px; font-size:17px`——这是对外页的**胶囊 CTA** 规格，直接提升会让全站管理台按钮变成 980px 胶囊。因此改为按控件基线（sm/md/lg = 26/32/40px、圆角 8px、行内小按钮 6px）新增尺寸变体，取值写入 `:root` CSS 变量，`.btn-*` 与 `.form-input-*` 共用。基类既有属性一律不动，确保未采用变体的调用点视觉不变——这也是尺寸只进变体类、不改基类的原因。

**决策三：恒定值列降级为行内次要信息，而非直接删除信息**

真实数据下恒定的列（如全为「无限制」「永不过期」「无代理」）不再独占列位，改为在主字段下方以次要文本呈现，并在取值偏离默认时予以视觉强调。不直接删除该信息，因为它在偏离默认时是重要的；也不保留独立列，因为绝大多数情况下它只是重复噪音。这样列数下降到常规视口内可容，横向滚动消失。

**决策四：恒无数据的区块采用条件渲染，而非删除实现**

账户余额区块在仅有订阅制账户的部署中恒为零值。选择条件渲染而非删除实现，因为接入按量计费账户的部署中该区块是有效的。判断依据取运行时数据而非配置开关，使同一份代码在不同部署下自适应。

此处与另一变更的取舍不同：那边选择直接移除无触发源的通知类型，因为那三类在代码层面根本没有发送调用点，属于永不可能有数据；而余额区块是「当前部署无数据、其他部署有数据」，性质不同。

**决策五：未启用能力不注册路由，与导航注入条件共用同一判断**

用户体系未启用时不注册对应路由，而不是保留路由并在页内提示未启用。理由是导航注入本已按能力开关条件执行，路由却无条件注册，二者不一致才导致「菜单看不到但手敲 URL 能进，且进去是一屏英文空数据」。让两者引用同一状态即可消除该不一致。代价是此前依赖手敲 URL 的访问方式失效，属预期内的破坏性变更并已在提案中标注。

**决策六：主题两控件合并为单一入口，但两项能力都保留**

顶栏两个主题控件曾被怀疑功能重叠，核查后确认不重叠：一个是配色方案选择（多套主色），一个是明暗模式切换（三态循环）。因此合并为单一入口下拉（面板内同时提供配色选择与明暗切换），而非删除其一。合并的收益是顶栏只占一个控件位且规格与相邻控件一致；同时可移除其中纯装饰的内部结构。

**决策七：对外展示页归统到管理台视觉基线**

统计页与落地、教程、引导页改用管理台的底色、卡片与控件规格，品牌色仅保留为主按钮与高亮色。考虑过「仅统一控件尺寸、保留各自视觉风格」，最终选择完整归统，取舍是牺牲对外展示的视觉冲击力换取全站一致性与维护成本下降（三份各约 260 行的 scoped 导航样式可一并收敛）。

**决策八：同构页面抽公共组件，差异走参数**

两个使用记录页结构几乎完全一致，差异集中在实体标签、取数方式、筛选维度与一个可选列。抽为单一表格组件并以参数传入差异，而非继续维护两份实现。判断标准是差异维度少且可枚举；若差异涉及交互流程本身，则不适合强行合并。

## Risks / Trade-offs

**[改动面覆盖几乎全部视图，回归范围大] → 缓解**：按决策一的四步顺序推进，每步产出可独立验证与回滚的提交。前两步只动样式基础，可先单独发布观察；后两步按页面分批进行。

**[样式去重可能意外改变视觉，因当前表现依赖三份定义的级联结果] → 缓解**：去重前后对关键页面做视觉比对，确认按钮、输入框、卡片表现一致。若发现某处外观依赖被删除的重复定义，说明该处本就依赖不确定行为，应在基线中显式表达而非恢复重复。

**[恒定值列降级后，偏离默认的取值可能被忽略] → 缓解**：降级后的次要文本在取值偏离默认时使用区别样式强调，并在规格中以场景固定该行为。

**[对外页视觉归统会明显改变外部访客的第一印象] → 权衡接受**：这是用户明确选择的方向。收益是全站一致与维护成本下降，代价是失去渐变风格的视觉冲击。

**[未启用能力改为路由不注册，属破坏性变更] → 缓解**：已在提案中标注 BREAKING。影响面仅限此前手敲 URL 访问这两页的操作方式，且这两页在未启用状态下本就只显示空数据，实际能力未减少。

**[分批发布期间可能出现新旧规格混排] → 权衡接受**：混排期视觉不一致但功能正常。可通过按页面分批而非按控件类型分批来缩小单次不一致范围。

## Migration Plan

1. 第一步：移除 `global.css` 重复定义段，使 `.btn`、`.form-input`、`.card`、`.stat-card` 各自唯一。构建后比对关键页面视觉，确认无变化。
2. 第二步：为 `.btn` 补 sm/md/lg 尺寸变体（取值来自 `LandingView` / `StartView` 已有 scoped 规格），确立卡片与表格的基线取值。此时页面尚未替换，视觉应保持不变。
3. 第三步：按页面分批替换手写内边距与圆角为基础类，同批完成该页的表格对齐、恒定值列降级、空转区块条件渲染、冗余文案合并。每批独立验证。
4. 第四步：路由条件注册、主题入口合并、暗色变体补齐。
5. 第五步：抽取共用组件（使用记录表格、对外页导航与页脚、统计卡），移除死代码与死分支。
6. 每步重新构建并发布 SPA 产物；纯前端变更，无需重启后端。
7. 回滚策略：各步为独立提交，按提交 revert 后重新构建发布即可。第一、二步若需回滚不影响页面；第三步之后回滚需连带回滚对应页面的替换提交。

- API Keys 已删除子页在软删除记录为空时恒为空态。本变更按能力暴露规则处理其可达性，但该子页是否长期保留、还是并入主表的筛选维度，需产品侧决定。
